## gpui spike

Pinned revision: zed `670a779a5ed9e7161c97aa4f998d395c207d5631`, toolchain
1.98.1. The harness is `crates/ossteam-gui/examples/spike.rs`. It opens a
window and prints one JSON line with the time to first presented frame
(measured from process start), the scale factor, the reported appearance,
and the result of a clipboard write/read round trip.

```sh
cargo run --release -p ossteam-gui --example spike
```

### Linux x86_64: Arch Linux, Hyprland 0.56.2 (Wayland), 1× scale, 2026-10-17

| Measure | Result |
|---|---|
| Window opens | yes |
| First frame, release, warm (5 runs) | 154.6 / 154.8 / 155.3 / 156.3 / 180.1 ms |
| First frame, `ossteam-gui` debug build, daemon running | ~250 ms warm; 2.37 s on the very first run (cold caches) |
| Scale factor | 1 (fractional and 2× scales not tested yet) |
| Clipboard round trip | **failed in 5 of 5 runs** — open item |
| Appearance at first frame | reported `Light` while the desktop is dark — open item |

Open items:

1. **Clipboard.** Writing then immediately reading the clipboard returned
   something else. A likely cause is Wayland's rule that only a client that
   currently has keyboard focus, or that has a recent input serial, may set
   the selection. The spike window may not have had focus yet when it wrote.
   This needs a test where the clipboard is written after the window gains
   focus, and a test under X11 (`DISPLAY`), before it can be called a gpui
   bug or a test artifact.
2. **Appearance.** In the first frame, the window reported `Light` on a
   dark desktop. `ossteam-gui` observes appearance changes and does render
   dark, as shown in screenshots, so the correct value arrives after the
   first frame. On Linux that is probably the asynchronous portal settings
   reply. Find out whether this causes a visible light flash at startup
   (GUI-4).
3. **DPI.** Test at 1.5× and 2× on Wayland, on X11, and on Windows and
   macOS.
