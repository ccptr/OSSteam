## gpui spike

Pinned revision: zed `670a779a5ed9e7161c97aa4f998d395c207d5631`, toolchain
1.98.1. The harness is `crates/ossteam-gui/examples/spike.rs`. It opens a
window and prints one JSON line with the time to first presented frame
(measured from process start), the scale factor, the reported appearance,
the result of clipboard write/read round trips, and each frame drawn and
each appearance change with its time. It waits 3 s before it reports; a
key pressed in that time (`wtype a`) tries the clipboard with an input
serial, and `OSSTEAM_SPIKE_CLIPBOARD=<text>` checks reading text another
client put there (`wl-copy <text>`, `xclip`) at that key press.

```sh
cargo run --release -p ossteam-gui --example spike
```

Items:

1. **Clipboard: answered, not a gpui bug.** On Wayland a client may set
   the selection only with the serial of a key or pointer press, and gpui
   skips the write until it has one ("Skipping Wayland clipboard ownership
   request because no keyboard or pointer press serial has been received",
   `gpui_linux` `wayland/client.rs`). The spike wrote before any input, so
   the write never happened. After a key press both directions work on
   Wayland and X11, which is how the GUI uses the clipboard (Ctrl-C,
   Ctrl-X, Ctrl-V in a text field).
2. **Appearance: fixed.** On Linux gpui starts every window as `Light` and
   asks the desktop portal (`org.freedesktop.appearance color-scheme`)
   asynchronously; the answer comes 2 to 4 ms after the first presented
   frame. A screen recording showed `ossteam-gui` presenting two light
   frames on a dark desktop, a visible flash (GUI-4). The GUI now asks the
   portal itself on a thread started with the process
   (`theme::StartupAppearance`, waited for at most 50 ms when the window
   opens) and draws with that answer until gpui reports an appearance
   other than the one it opened the window with. Not yet seen on a light
   desktop; macOS and Windows report the appearance at once and skip the
   query.
3. **DPI: Wayland done; X11, Windows and macOS left.** At 1.25× on
   Hyprland, and at 1.5× and 2× on a headless sway 1.12
   (`WLR_BACKENDS=headless`, which leaves the desktop alone), the
   spike's first two frames are drawn at scale 1 and the rest at the
   output's scale: gpui opens every window at 1 and learns the scale
   from the compositor only after the first commit. `ossteam-gui`'s
   first frame is at scale 1 too (`OSSTEAM_GUI_STARTUP_TIMING`); 40
   screenshots in a loop at 2× (`grim`) caught no frame at scale 1, so
   whether it shows blurred is still not seen. The library has not
   arrived by then: at 1.5× and 2× the GUI asks only for 2× capsules
   from its first library frame. The Login page at 2× and the library
   grid at 1.5× and 2× are sharp and laid out as at 1×. A window whose
   scale rose from 1 to 2 kept its 1× capsules, since each image was
   asked for once; it now asks for the 2× ones then and shows the 1×
   ones until they arrive (`gui.md` §4.2). Checked by switching the
   headless output from 1 to 2 while watching which files the GUI
   opened, with the bench's capsules carrying `image2x` as Steam's do.
